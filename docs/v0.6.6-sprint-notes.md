## ✅ Sprint B (P1 - Auditability & Navigation) - COMPLETED

### P1.1: CreatedAt Timestamp ✅

- **Added**: `CreatedAt` property to `Transaction` domain entity
- **Migration**: `20260201120045_AddTransactionCreatedAt` (3-step: nullable → update → required)
- **Ordering**: Transactions now sorted by `BookedOn DESC → CreatedAt DESC → TransactionId DESC`
- **Purpose**: Stable ordering for transactions on same date, auditability

### P1.2: Running Balance ✅

- **Added**: Running balance calculation in `ReportingReadRepository.GetAccountMovementsAsync`
- **Algorithm**:
  1. Calculate starting balance (all splits before period)
  2. Get movements in chronological order
  3. Accumulate balance transaction by transaction
  4. Return balance for each paginated movement
- **UI**: New "Balance" column in AccountMovementsPage with color coding (negative = red)

### P1.3: Navigation from Movements ✅

- **Status**: Already implemented
- **Feature**: Click on movement row calls `NavigateToTransaction(Guid transactionId)`
- **Location**: `AccountMovementsPage.razor` line ~160

### P1.4: Liability Payment Support ✅

- **Status**: Already implemented via Transfer type
- **Discovery**: `QuickEntryType.Transfer` specification allows:

  ```csharp
  FromAllowed: { AccountNature.Asset, AccountNature.Liability }
  ToAllowed: { AccountNature.Asset, AccountNature.Liability }
  ```

- **Usage**: Covers all liability payment scenarios:
  - Bank → Credit Card (pay credit card bill)
  - Bank → Loan (pay loan installment)
  - Savings → Mortgage (pay mortgage)
  - Cash → Credit Card
- **Location**: `DashboardPage.razor` lines 486-511
- **Conclusion**: No new implementation needed. Transfer type handles liability payments correctly with proper double-entry accounting.

## 🔍 Technical Discoveries

1. **SQLite Limitation**: Cannot use non-constant default values in ALTER TABLE
   - **Workaround**: 3-step migration (nullable → update → required)

2. **Balance Calculation**: Must respect transaction chronology
   - **Solution**: Calculate starting balance, then accumulate in order

3. **Pagination Complexity**: Running balance requires full history traversal
   - **Solution**: Query all transactions up to current page, accumulate, then paginate

4. **Transfer Flexibility**: Already supports complex account nature combinations
   - **Benefit**: No need for dedicated "LiabilityPayment" type
