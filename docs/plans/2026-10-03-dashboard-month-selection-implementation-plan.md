# Implementation Plan: Dashboard Month Selection

## Scope and assumptions

This plan implements OpenSpec change `dashboard-month-selection`. The Dashboard selects complete calendar months only: a historical month is evaluated at its last calendar day, while the active month is evaluated at today. The Dashboard URL owns this local reporting state through `year` and `month` query parameters. Quick Entry remains a current-time workflow and is intentionally excluded.

## 1. Add Dashboard period state and controls

- Update `src/FamilyFinances.Web/Components/Pages/Dashboard/DashboardPage.razor` to read optional `year` and `month` query parameters, normalize absent, invalid, and future selections to the current period, and maintain explicit selected-year and selected-month state.
- Render accessible, localized year and month controls in the same context row as the data-sufficiency notice. Use the current-year month limit and stack the controls beneath the notice at narrow breakpoints. Preserve the controls in that context row when no notice is rendered.
- Update URL state without losing the selected values, reload the Dashboard only after a valid selection change, and continue routing data access through `ReportsApi` and `TransactionsApi`.
- Update `SharedResource.resx`, `SharedResource.es-ES.resx`, and `SharedResource.en-US.resx` with the labels and accessible names required by the controls.
- Add bUnit tests in `tests/FamilyFinances.Web.Tests/Features/Dashboard/DashboardPageTests.cs` for default state, URL restoration, allowed month options, selection-driven reload, and the notice-row layout contract.

## 2. Apply the selected period to Dashboard data and navigation

- Pass the selected year and month to `ReportsApi.GetDashboardOverviewAsync` and use the returned `AsOf` value consistently for KPI, chart, badge, export, and year-to-date calculations.
- Keep group-report URLs generated by `BuildPinnedGroupReportUrl` period-aware and add coverage that verifies the selected values are propagated.
- Audit Dashboard outbound analytics links and pass the selected year and month to each compatible target. Do not add a historical context to Quick Entry or authentication links.
- Update existing Dashboard CSV tests so filenames, metadata, and rows correspond to refreshed selected-period data.

## 3. Scope latest expenses by calendar month

- Extend `ITransactionRepository.ListLatestExpensesAsync`, `ListLatestExpenseMovementsHandler`, `TransactionRepository`, and `TransactionsController` with optional, jointly validated `year` and `month` inputs.
- When both values are supplied, filter transactions by `BookedOn >= monthStart` and `< nextMonthStart` before applying the existing Expense-nature filter, deterministic descending order, and fixed limit of six. Preserve the no-parameter behavior for existing callers.
- Update `TransactionsApi.GetLatestExpensesAsync` to send the selected year and month together and keep its authorization, cancellation, and error behavior.
- Update `DashboardPage` to load the period-scoped latest expenses and export precisely the visible rows.
- Update `openspec/api-spec.yaml` with the optional query parameters, response behavior, validation responses, and unchanged authorization requirement.

## 4. Test data contracts and behavior

- Extend application handler tests in `tests/FamilyFinances.Application.Tests/Ledger/Transactions/` to verify forwarding of a complete period and preservation of the no-period call.
- Extend API integration tests in `tests/FamilyFinances.Api.IntegrationTests/Ledger/Transactions/TransactionsApiTests.cs` using the existing real relational test factory. Cover month filtering, exclusion of transactions outside the month, six-item limit, equal-date identifier ordering, invalid/incomplete period rejection, authorization, and no-parameter compatibility.
- Extend API-client tests in `tests/FamilyFinances.Web.Tests/Api/TransactionsApiAdditionalTests.cs` to verify the requested query string and authorization header.
- Keep component tests behavior-oriented: assert rendered selected-period values, refreshed movement rows, exports, and target URLs instead of private component state.

## 5. Documentation and verification

- Mark the OpenSpec task checklist as completed only after the implemented behavior and tests are present. If implementation requires a material deviation, update the change proposal, design, and delta specs before verification.
- Run `dotnet test FamilyFinances.sln --no-restore`, `dotnet build FamilyFinances.sln --no-restore`, `git diff --check`, and `openspec validate dashboard-month-selection --strict`.
- Verify the OpenAPI YAML with the repository's configured validation command, if available.

## Explicit non-goals

- No separate historical-dashboard page, arbitrary date range, generic reporting filter framework, persistence of user filter preferences, or new database schema.
- No changes to existing economic-state filter behavior, Quick Entry transaction dates, or unrelated report routes.
